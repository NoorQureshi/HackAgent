# bench/ — SploitAgent benchmark harness

Do SploitAgent skills make an AI agent measurably better at offensive security?
This harness proves it with numbers instead of claiming it: it runs Claude Code
headless against a local intentionally-vulnerable target in two arms — **skills**
vs **baseline** — identical except for skill access, and scores both from the
target's own log. Results: [RESULTS.md](RESULTS.md).

## Methodology

- **Target:** OWASP Juice Shop (pinned release, currently v20.2.0, 116 challenges),
  downloaded as the prebuilt darwin/arm64 zip and run on `127.0.0.1:3000`.
  No Docker required: the zip's native modules need node 22, which the adapter
  runs through the standalone binaries from the `node` npm package (`npx node@22`).
- **Two arms, one difference.** Each trial gets a fresh workspace scaffolded like
  `sploit new` does (`scope.txt`, `plan.md`, `notes.md`, `findings/`,
  `.sploit/activity.jsonl`). The skills arm adds a `skills/` symlink, `AGENTS.md`,
  and `CLAUDE.md`; the baseline arm doesn't. Both arms run with the same model,
  the same neutral prompt ([prompts/juice-shop.txt](prompts/juice-shop.txt) — no
  technique hints, no skill mentions), and identical flags
  (`--setting-sources project --strict-mcp-config` + empty MCP config, so no
  user-level settings leak into either arm). The baseline additionally gets
  `--disable-slash-commands`, which hides the SploitAgent skills a
  `sploit install` user has in `~/.claude/skills` — verified by a dry run in which
  the baseline agent reports zero skills available while the default run lists
  200+.
- **Scoring is un-gameable.** Juice Shop logs every solved challenge
  (`Solved N-star <key> (<name>)`). The harness parses the target's log — not
  anything the agent says it did — via [target_juiceshop.sh](target_juiceshop.sh)
  (`up / down / reset / status / solved / count`; the interface is generic so a
  second target adapter can be added without touching the runner). Between trials
  the target restarts for a clean slate.
- **Budgets.** `--max-minutes` terminates the agent at the deadline;
  `--max-turns` caps turns. Every run writes `bench/runs/<id>/result.json`
  (solved list + count, minutes, turns, cost, tokens, model).

## Reproduce

```console
$ python3 bench/run.py setup                                    # one-time: download the target
$ python3 bench/run.py run --arm skills   --trials 3            # full A/B:
$ python3 bench/run.py run --arm baseline --trials 3            #   3 trials × 2 arms
$ python3 bench/run.py report                                   # regenerate RESULTS.md
```

Defaults: `--trials 3 --max-minutes 30` (add `--max-turns T` to cap turns,
`--model <name>` to change the model, default `sonnet`).

> **Cost warning:** every trial is a real, unattended Claude Code session burning
> your Claude usage — up to `--max-minutes` per trial. The full A/B above is
> 6 × 30 minutes of agent time. Smoke-test first with
> `--trials 1 --max-minutes 10`.

> **Ethics:** the harness only ever attacks a local intentionally-vulnerable
> training app on `127.0.0.1`. Do not point the prompt or the target adapter at
> anything you don't own. Benchmarks, like skills, are for authorized work only.

## Files

| path | purpose |
|---|---|
| `run.py` | `setup` / `run` / `report` — download target, run trials, aggregate results |
| `target_juiceshop.sh` | target lifecycle + log-based scoring adapter |
| `prompts/juice-shop.txt` | the one neutral prompt both arms receive |
| `RESULTS.md` | generated results table — committed, regenerated by `report` |
| `.targets/` | downloaded target (gitignored) |
| `runs/` | per-trial workspaces + `result.json` (gitignored) |

CI never *runs* the benchmark (it needs Claude auth and a live target); it only
compile-checks these files via `tools/check.sh`.
